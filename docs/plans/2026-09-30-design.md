# universal-email-mcp — design plan (draft)

Status: **design baseline** · 2026-09-30 · M1 is implemented; what is left and in
which order: [`2026-10-09-roadmap.md`](2026-10-09-roadmap.md).

An MCP server that bridges standard mailboxes (IMAP, SMTP, POP3) to AI assistants
(Claude, ChatGPT, any MCP client). Vendor neutral, Apache-2.0, built to run as a
multi-user service for a company (reference deployment: Google Cloud Run) and as a
simple local single-user server.

---

## 1. Goals and non-goals

**Goals**

- Any standards-compliant mail server — no provider SDKs, no Gmail/Graph APIs.
  **Target audience: everyone who is *not* on Gmail/Google Workspace** (those use
  the dedicated Gmail connector) — hosters like united-domains, IONOS, Strato,
  World4You, Hetzner, all-inkl, self-hosted Dovecot/Postfix, Exchange on-prem, …
  Many of them are password-only and some customers still rely on POP3.
- **Several mail accounts per user** (IMAP, POP3, SMTP in any combination) behind
  one set of tools: search spans all incoming accounts, sending picks the right
  identity automatically.
- **Self-service web portal** where each user manages their accounts, sees their
  own activity, controls which AI clients have access, and deletes everything.
- **Smart retrieval**: time-window listing, fuzzy matching of people, subjects and
  folders (rapidfuzz), contact lookup from mail history — with firm limits.
- **Multi-user remote server**: the AI client only ever holds an MCP token.
- **Corporate grade**: encrypted credentials, bounded resource use, pseudonymous
  audit logging, admin policy (send on/off, recipient domains, rate limits),
  documented GDPR posture.
- **Safe against prompt injection** by design: mail content is untrusted input and
  the server — not the model — gates outbound mail.
- Stateless and cheap on a scale-to-zero host.
- Newest stack: MCP Python SDK 2.x (`MCPServer`), protocol 2026-07-28, Python ≥ 3.12.

**Non-goals (v1)**

- Permanent deletion of user mail. Deleting = moving to Trash, via its own
  `delete_messages` tool (§7).
- Push notifications (IMAP IDLE) — incompatible with scale-to-zero.
- Calendars/contacts (CalDAV/CardDAV), JMAP — later phases.
- Gmail / Google Workspace: out of scope (use the Gmail connector). Microsoft 365
  needs XOAUTH2 (passwords are off for IMAP/POP there) — only if there is demand;
  the auth layer keeps a slot for token-based SASL so it can be added later.
- A full webmail client. The portal manages connections and offers a read-only
  **message viewer** for links from the chat (§6.2) — no composing, no inbox UI.

## 2. Name

`universal-email-mcp` — free on PyPI and npm; the only GitHub namesake is a stale
0-star repo. `imap-mcp` and `mail-mcp` are crowded (npm/PyPI/GitHub). Proposal:
keep it. Python package `universal_email_mcp`, CLI `universal-email-mcp`.

**Gaps nobody fills** — our reason to exist: a self-hostable multi-user remote
server with built-in OAuth and a self-service portal; one tool surface across many
accounts and protocols (incl. POP3); fuzzy retrieval; pseudonymous audit logs;
central admin policy; a *human* send gate (every existing "confirm" is a flag the
model sets itself); scale-to-zero-friendly IMAP handling.

**Ideas borrowed**: write tools not registered when disabled; message identity =
(account, folder, UIDVALIDITY, UID) and UID-scoped operations only; fenced
untrusted content with zero-width/tag-breakout neutralisation; error results with
`code` + `hint`; hard response bounds + cursors; special folders by role; send
rate limits.

## 4. Architecture

```
 MCP client (Claude.ai / Desktop / ChatGPT / CLI)          Browser
    │  Streamable HTTP, Bearer <MCP access token>             │ session cookie
    ▼                                                         ▼
 ┌────────────────── universal-email-mcp (container) ──────────────────┐
 │ Starlette app                                                        │
 │  ├─ /mcp            MCPServer (stateless 2026-07-28 + legacy)        │
 │  ├─ /.well-known/*  AS + protected-resource metadata                 │
 │  ├─ /authorize /token /revoke /register   OAuth 2.1 AS               │
 │  ├─ /portal/*       self-service portal (login, accounts, clients,   │
 │  │                  activity, delete) — also hosts OAuth login+consent│
 │  └─ /health /ready                                                   │
 │                                                                      │
 │ core:  tools → policy → account router → backends (IMAP/POP3/SMTP)   │
 │        retrieval: header index cache · rapidfuzz matching            │
 │ state: Store (memory | firestore | sqlite later) · Cipher (AES-GCM)  │
 │ audit: JSON events → stdout → Cloud Logging; own-activity feed       │
 └──────────────────────────────────────────────────────────────────────┘
    │ IMAPS 993 / POP3S 995 / SMTPS 465 / SMTP+STARTTLS 587 (cert-verified)
    ▼
 mail servers (united-domains, Dovecot, Exchange on-prem, any hoster …)
```

**Two run modes from one code base**

| Mode | Transport | Users | Accounts & credentials | Store |
|---|---|---|---|---|
| `local` (stdio) | stdio | 1 | TOML config file, passwords in OS keyring / env | none (local cache only) |
| `remote` | Streamable HTTP | many | portal → encrypted in Store | memory / Firestore (/ SQLite later) |

**Statelessness.** Every tool call is self-contained: bearer token → session →
user → accounts (decrypted on demand) → backend connections → answer. Nothing
important lives only in process memory, so any instance can serve any request and
scale-to-zero loses nothing. In-process caches (connections, header index) are
pure optimisations.

**Transport.** Protocol 2026-07-28 clients get the sessionless transport, where
confirmations are multi-round-trip requests whose state is sealed with the SDK's
`RequestStateBoundary` / `AESGCMRequestStateCodec` (principal-bound, shared key from
Secret Manager). Older clients get legacy Streamable HTTP in **stateless** mode: it
needs no session affinity, but has no back-channel, so it cannot elicit — those
clients always get the confirmation *fallback* (§8). An operator who wants
in-chat confirmations for legacy clients can run stateful legacy mode with a
single instance (or session affinity), documented as an option.

**Connections.** Short-lived by default, optional small per-instance LRU pool
(idle TTL ~60–120 s, ≤ 2 connections per account, global cap per instance) because
hosters cap concurrent connections per mailbox. All mail I/O runs in worker
threads (`imapclient`, `poplib`, `smtplib`) with strict timeouts; fan-out across
accounts is parallel with a per-account deadline.

## 5. Accounts model

A **user** owns any number of **accounts** and **identities**:

```
User ─┬─ Account "Work"      IMAP  imap.company.example perms: read, organize, drafts
      ├─ Account "Archive"   IMAP  archive.example    perms: read            (read-only)
      ├─ Account "Old POP"   POP3  pop.hoster.at      perms: read            (POP: no folders/flags)
      ├─ Account "Shared"    IMAP  office@company     perms: read, organize
      └─ Identities (senders)
           ├─ ★ alice@company.example   "Alice Example"   via SMTP smtp.company.example
           │      drafts+sent copies → Account "Work", signature …
           └─   office@company.example  "Company Office"  via SMTP (office creds)
                  sent copies → Account "Shared"
```

- **Account** = one incoming mailbox (IMAP or POP3) + credentials + **permissions**
  (`read`, `organize` = mark/move, `delete` = move to Trash, `drafts`), capped by
  what the protocol can do and by admin policy.
- Identities carry the **`send`** permission; grants (below) scope both per client.
- **Identity** = a sender: from-address(es), display name, SMTP transport +
  credentials, signature, and which IMAP account receives its Drafts / Sent copies.
  Exactly one identity is the **default**. An identity without a linked IMAP
  account can still send (no Sent copy, noted in the confirmation).
- **Adding a mailbox** from a preset creates the usual pair (IMAP account +
  identity with the same credentials) in one step; advanced users can split them.
- **Sender selection** when replying/forwarding: the identity whose address
  received the original (To/Cc/Delivered-To match) → the default identity of that
  account → the global default. The chosen sender is always shown in the
  confirmation. New mail: default identity unless the tool call names one.
- **Tools** take an optional `accounts` filter (names); search defaults to all
  incoming accounts, results carry the account name. `account_info` tells the
  model exactly what each account/identity may do.
- **Per-client grants**: at OAuth consent the user chooses which accounts and
  identities this AI client may use (e.g. Claude: all read, may send as alice@;
  a test client: Archive read-only). Stored on the session; enforced per call.

**Which mail servers may users add?** One operator setting, a comma-separated
list, e.g. `MAIL_SERVERS=united-domains,mail.example.com`:

| `MAIL_SERVERS` | Portal behaviour |
|---|---|
| one entry | fixed: the form asks only for address + password |
| several entries | dropdown to pick the server; nothing else allowed |
| unset / empty | user enters the server (prefilled by autodiscovery: Thunderbird ISPDB, autoconfig, RFC 6186 SRV) |

Each entry is either a **built-in preset name** (`united-domains`, … — hosts,
ports and TLS modes for IMAP/POP3/SMTP, plus folder-name hints) or a **hostname**
(same host for all protocols, standard TLS ports 993/995/465, capabilities probed
on first use). The same list is used in `local` mode as a convenience only.

Free entry (unset list) comes with SSRF guards: only ports 993/995/465/587; the
hostname is resolved once per connection, every address is checked (public
unicast only — no private, loopback, link-local, CGNAT, metadata ranges), the
socket connects to the *checked IP*, and the hostname is used only for TLS SNI
and certificate verification (no DNS-rebinding window); TLS verification is
mandatory. The same connector is used for CIMD fetches.

**Free entry never applies to the portal identity** — see §6.

## 6. The user portal

Server-rendered HTML (Starlette + Jinja2, minimal JS, no third-party assets,
strict CSP). Translatable from the start, English first; German follows as the
second language, the operator sets the default language and users can switch
(see `AGENTS.md`). The same pages serve the OAuth login + consent step, so
there is one place users ever type a password.

| Page | What the user can do |
|---|---|
| Sign in | e-mail + password (see "portal identity" below) |
| Accounts | add (preset or autodiscover or manual), test connection, edit permissions, change password, remove |
| Identities | sender addresses, display name, signature, SMTP account, default ★ |
| Connected AI clients | list sessions (client name, created, last used, granted accounts), change grants, revoke |
| Activity | own recent events: logins, tool calls (tool, account, counts), sends (recipient count, time) — last 30 days |
| Pending approvals | send requests waiting for browser approval (see §8), approve/decline |
| Privacy | download my data (settings + activity, no passwords), **delete everything** (accounts, sessions, activity; confirmed) |

**Portal identity.**
1. **Mailbox login** (v1): the user's *primary* address + its password, verified
   live against the IMAP server **the operator assigned to that address's
   domain** — never a server the user supplies (otherwise anyone could claim
   `alice@company.example` against their own server and take over Alice's
   record). Remote mode therefore requires `LOGIN_DOMAINS`, a mapping of mail
   domains to servers, e.g. `LOGIN_DOMAINS=company.example=united-domains`
   (entries as in `MAIL_SERVERS`; if `MAIL_SERVERS` has exactly one entry it is the
   default server). Sign-in with any other domain is refused. The user record is
   keyed by the pseudonymous primary address; further accounts hang off it and
   may use free entry if the operator allows it.
2. **OIDC SSO** (later, see `TODO.md`; any OpenID provider): stronger (MFA,
   offboarding via the IdP); mailbox passwords are then only mail credentials.

Security: sessions in secure/HttpOnly/SameSite cookies, CSRF tokens, re-enter
password for sensitive actions (add account, delete all, grant send), rate
limits, portal events in the audit log.

### 6.1 OAuth toward MCP clients and sessions

- The server is its own OAuth 2.1 authorization server: authorization code + PKCE
  (S256), RFC 8707 `resource` → token audience, RFC 9728 protected-resource
  metadata, RFC 9207 `iss` in the authorization response, refresh-token
  rotation, revocation.
- **Client identification**: Client ID Metadata Documents (CIMD) — preferred by
  the 2026-07-28 spec and used by Claude's hosted connector identity. The SDK
  has no server-side CIMD, so we implement it (HTTPS-only fetch, size/time
  limits, the SSRF-safe connector of §5, caching). Dynamic Client Registration
  stays as a fallback (the spec prefers CIMD; DCR is still widely used — exact
  normative status to be checked against the spec text), limited by a
  redirect-URI host allowlist.
- `/authorize` → portal sign-in (if needed) → **consent page with grants**
  (which accounts/identities this client may use) → code → tokens. The spec
  forbids collecting passwords via form elicitation; the portal is the
  mandated browser path.
- Tokens are opaque random strings, stored only as SHA-256 hashes.
- **Session lifetime**: access token 1 h, refresh 30 days sliding, absolute max 90
  days — operator-configurable; unlimited is allowed but documented as weaker
  (a leaked refresh token then never expires on its own; users can still revoke
  in the portal).
- Mail password changed at the server → tool calls on that account fail with a
  clear `reauth_required` error naming the portal page to fix it; other
  accounts keep working.

### 6.2 Message viewer: from the chat to the full mail and attachments

Chat clients can't receive large files, and a text summary is not always enough.
So every message in tool results carries a **viewer link** into the portal, e.g.
`https://<server>/m/<opaque message id>` — the user clicks it in the chat and sees
the mail in the browser, already signed in, without opening a mail client.

| View | Content |
|---|---|
| Message | headers (from/to/cc/date/subject), text body; HTML version in a sandbox (below) |
| Thread | the whole conversation, chronological, each message expandable |
| Raw headers | full header block (Received chain, SPF/DKIM/DMARC results, Message-ID …) |
| Source | the raw RFC 822 message (`.eml` download) |
| Attachments | list with size/type, **download** each (or all as ZIP), streamed from IMAP |

- **Authorisation**: the link itself grants nothing. Opening it requires a portal
  session (sign in if needed) of the user who owns the account; grants still
  apply. Ids are opaque and include the account, so guessing is useless and a
  link pasted into someone else's browser shows nothing.
- **Untrusted content in the browser**: mail HTML is rendered only inside a
  sandboxed `iframe` (`sandbox` without scripts, strict CSP on the frame
  response: no scripts, no remote images/fonts/styles — optional "load images"
  click), links rewritten to open in a new tab with `rel=noopener noreferrer`.
  Attachments are served with `Content-Disposition: attachment`,
  `X-Content-Type-Options: nosniff` and a `sandbox` CSP, never inline as HTML.
  A separate content origin (subdomain) for user content is recommended when the
  deployment can provide one.
- **Streaming and limits**: attachments are streamed part-by-part from IMAP
  (`BODY.PEEK[<part>]`), never buffered whole; size limits per operator.
- **Audit**: `viewer.open`, `viewer.raw`, `attachment.download` (count, size
  bucket, content-type family) — no names or content.
- **Local mode**: an optional viewer on `127.0.0.1` with a random per-run token
  in the URL, or `get_attachment(save_to=…)` into a configured download folder.

## 7. Tools

Message references are opaque ids encoding (account, folder, UIDVALIDITY, UID);
a UIDVALIDITY change makes old ids fail cleanly instead of hitting the wrong mail.

| Tool | Purpose | Kind | Phase |
|---|---|---|---|
| `account_info` | accounts, identities, permissions, capabilities, quota, policy | read | 1 |
| `list_folders` | folders ("labels") per account as a tree (groups like `Clients/…`), with role (inbox/sent/drafts/trash/junk/archive) and counts | read | 1 |
| `list_messages` | time window ("this week", since/before) across accounts, compact summaries, cursor | read | 1 |
| `search_messages` | structured query (from/to/subject/body/date/unread/flagged/attachment) across accounts; `fuzzy=true` for approximate matching | read | 1 |
| `get_message` | headers, text body (HTML→text), attachment list; bounded, paged | read | 1 |
| `get_thread` | conversation around a message (References/In-Reply-To, across INBOX + Sent + accounts), chronological, quoted text collapsed, each message with its viewer link | read | 1 |
| `find_contacts` | people you've corresponded with, fuzzy name/address match, ranked by recency/frequency | read | 1 |
| `mailbox_overview` | per account: unread, recent, top senders in a window — for "what's new?" | read | 2 |
| `get_attachment` | small text/* inline, other files as embedded resource (size-capped); large files → viewer download link (§6.2); PDF/office understanding later (TODO.md) | read | 2 |
| `mark_messages` | seen/unseen, flagged (batch, capped) | organize | 1 |
| `move_messages` | to another folder (Archive, custom); fuzzy folder resolution; refuses Trash → use `delete_messages` | organize | 1 |
| `archive_messages` | move to the account's archive, following its scheme (e.g. `Archive/2026`), creating the year folder if needed (§7.2) | organize | 2 |
| `file_conversation` | move a message **and the rest of its conversation** (incl. own replies in Sent) into a folder, e.g. `Clients/Huber` (§7.2) | organize | 2 |
| `create_folder` | create a folder (e.g. a new client under `Clients/`); never deletes or renames | organize | 2 |
| `delete_messages` | move to Trash (recoverable), batch capped; **own tool, `destructiveHint`** so the chat UI can ask the user explicitly | delete | 1 |
| `create_draft` | new / reply / reply-all / forward, proper threading, auto sender | drafts | 1 |
| `update_draft` | replace a draft | drafts | 2 |
| `send_draft` / `send_message` | send — **human confirmation** (§8), Sent copy, draft removed | send | 1 |

POP3 accounts participate in `list_messages`, `search_messages`, `get_message`
and `get_attachment` (no folders, flags, moves). POP3 has no server-side search:
the server reads headers of the newest N messages (`TOP n 0`, capped, cached per
instance by UIDL) and filters locally. POP3 accounts are never modified
(no `DELE`).

**Delete is deliberately separate** from `move_messages`: many clients ask before
running tools annotated `destructiveHint: true` (and users can set "always ask"
per tool), and a separate tool keeps that possible. Annotations are only hints —
clients are not required to prompt — so they are a convenience, not a safety
control; the real controls are the per-account `delete` permission (off unless
granted) and Trash being recoverable. Moving to Trash uses `UID MOVE` (RFC 6851);
without MOVE it is `UID COPY` + `\Deleted` + `UID EXPUNGE` of exactly those UIDs
(requires UIDPLUS, RFC 4315 — otherwise the tool refuses). Permanent deletion is
not planned for v1.

Tools the effective policy forbids for this user/client are **not registered**
(or listed as unavailable), so the model never tries them.

### 7.1 Retrieval and fuzzy matching

IMAP `SEARCH` is exact substring matching — it misses typos, umlaut spellings
(Müller / Mueller / Muller), name order ("Example Alice"), and similar subjects.
Our approach:

1. **Header index per (account, folder)**: `FETCH` of ENVELOPE + a few headers for
   the requested time window (bounded, e.g. ≤ 2 000 messages per account per call),
   cached in-process keyed by UIDVALIDITY and extended incrementally by UID
   (`UID FETCH n+1:*`, filtering UIDs ≤ n client-side — `*` always matches the
   highest message). POP3 via `TOP`/UIDL. No mail content is persisted in the Store.
2. **Normalisation**: casefold, NFKD accent stripping *and* German transliteration
   (ä→ae …) so both spellings meet; address local-part + display name tokens.
3. **Matching** with `rapidfuzz` (MIT): `token_set_ratio` / `WRatio` over sender,
   recipients and subject, score threshold + top-k; exact server-side SEARCH is
   still used first when the query is precise (cheap, full-folder).
4. **Uses**:
   - `search_messages(fuzzy=true)` — "the invoice from Hubr last month";
   - `find_contacts` — builds a contact list from From/To/Cc of INBOX + Sent over
     a window (default 180 days, capped), ranks by frequency × recency;
   - **recipient check at send time**: an address counts as *trusted* only if the
     user has **sent** to it before (recipients of mail in Sent) or it is in an
     operator-configured internal domain. Merely *receiving* mail from someone
     does not count — otherwise the author of an injected mail would be
     "known". Untrusted addresses and look-alikes of trusted ones
     (`maria.muller@` vs trusted `maria.mueller@`, or a different domain) are
     flagged — catches typos and injection-driven exfiltration;
   - folder resolution: "move to invoices" → `INBOX.Rechnungen 2026`.
5. **Limits** (all configurable): max accounts per fan-out, per-account deadline
   (partial results are reported, not hidden), max headers scanned, max results,
   response size caps.

### 7.2 Folders as labels: filing, archiving, conversations

Many users sort mail into **hierarchical folders that act like labels** —
`Clients/Huber`, `Clients/Maier GmbH`, `Projects/2026-Website`, `Tax/2025` — and
expect the assistant to understand them. Target scenario:

> "Move the mail from Huber and my answer to the Huber client folder."

1. **Hierarchy-aware folder resolution.** Folder paths are split on the server's
   delimiter and namespace prefix (`INBOX.Clients.Huber` → `Clients / Huber`).
   Matching is fuzzy on *both levels*: the group ("client", "Kunde", "clients")
   and the leaf ("Huber", "huber gmbh", "Hubr"). Ambiguities (two good matches)
   are returned to the model as a choice instead of guessing; no match → offer
   `create_folder` under the matched group.
2. **Groups are discovered, not configured**: any folder with children is a
   potential group; `list_folders` can return the tree. Optionally the user names
   important groups in the portal/config (e.g. `Clients` = "clients / Kunden").
3. **`file_conversation(message, target)`** collects the conversation around the
   message — the message itself, earlier and later messages linked via
   Message-ID / In-Reply-To / References — **across INBOX, Sent and other
   folders of the same account**, shows what will move, then moves them all to
   the target (MOVE or COPY + UID EXPUNGE, §7). Bounded (max messages, time
   window); messages in other accounts are reported, not moved.
4. **Filing replies automatically.** When a reply is sent to a message that lives
   in a filed folder (e.g. `Clients/Huber`), the Sent copy can be placed there
   too. Per-identity setting `file_replies = sent | thread_folder | both`
   (default `sent`; `both` keeps Sent complete *and* files the reply).
5. **Archive.** Webmailers and clients have an "archive" action that moves mail
   into an archive folder, often split by year (`Archive/2026`) or month. The
   archive folder is found via SPECIAL-USE `\Archive` or name heuristics; the
   scheme (flat / yearly / monthly) is detected from existing children and can be
   overridden per account. `archive_messages` uses the message date to pick the
   sub-folder and creates it if missing. (For each preset the actual scheme is
   verified with `probe` against a real mailbox.)
6. **Label management**: start with listing (`list_folders`, tree view) and
   creating (`create_folder`, e.g. a new client under `Clients/`). Renaming,
   moving and deleting folders come later (`TODO.md`) — they affect many
   messages at once and need the same care as deletion.
7. All of this needs the `organize` permission; nothing here deletes mail.

### 7.3 Output format: tables for the chat, structured data for programs

Every list-like result (search results, `list_messages`, threads, folders,
contacts) is returned in **two forms at once**, as MCP allows:

- **`content` (text) — a compact Markdown table** that chat UIs render directly
  and models tend to pass through, e.g. for a thread:

  | # | Date | From | To | Subject | 📎 | Link |
  |---|---|---|---|---|---|---|
  | 1 | 2026-09-28 09:14 | Huber, Anna | me | Angebot Website | 1 | [open](…/m/…) |
  | 2 | 2026-09-28 11:02 | me | Huber, Anna | Re: Angebot Website | – | [open](…/m/…) |

  followed by a one-line footer (e.g. "3 of 12 shown · more: cursor=…" or
  "account Archive timed out — partial result").
- **`structuredContent` (JSON, with an `outputSchema`)** with the full typed
  data (ids, all addresses, flags, sizes, viewer URLs) for clients and agents
  that process results programmatically.

The server `instructions` and tool descriptions tell the model to present list
results as tables, keep the viewer links, and show message bodies as quoted text
below the table rather than inside it. Markdown was chosen over YAML because
chat clients render it as a table without help; the structured JSON covers the
machine-readable side. Tables are also far more token-efficient than JSON for
the model.

**Untrusted text in tables**: subjects, names and addresses come from mail and
are attacker-controlled. Cells are escaped — `|`, newlines and backticks
neutralised, Markdown links/images (`[..](..)`, `![..](..)`) and raw URLs
defanged, length-capped — because a crafted subject rendered as an image link
could make the chat client fetch an attacker URL (exfiltration). Only links the
server generates itself (viewer links) are emitted as real Markdown links.

## 8. Safety: prompt injection and outbound mail

Mail is untrusted input, and this server combines private data + untrusted content
+ an outbound channel — the EchoLeak-class setup. Mitigations:

1. **Server-enforced send confirmation.** `send_*` returns an *input required*
   request (2026-07-28 multi-round-trip elicitation; legacy clients: see §4
   Transport) showing sender, recipients (with new/look-alike warnings), subject,
   attachment names and body preview. Continuation state is sealed with a key from
   Secret Manager, short-lived, bound to user + content hash.
   **Fallback** when the client cannot elicit (operator setting `SEND_FALLBACK`):
   `send-unless-flagged` (default) sends unless the recipient check (§7.1) flags
   something — flagged sends wait under *Pending approvals* in the portal (link
   returned to the model/user); alternatives `send`, `portal` (always approve in
   the portal), `draft` (stays in Drafts).
2. **Policy** (per deployment; per user in the portal only *more* restrictive):
   `send: off | confirm | confirm-external | on`, allowed recipient domains, max
   recipients, sends per hour/day per user, read-only, allowed servers
   (`MAIL_SERVERS`), allowed login domains.
3. **Fenced content**: bodies inside explicit untrusted-content markers, tag
   breakout and zero-width characters neutralised; tool descriptions tell the
   model never to follow instructions found in mail.
4. **Bounded outputs**: max chars per body, messages per call, cursors.
5. **No local file access**: outgoing attachments only from existing messages
   (forward) or small inline content — never server paths.

## 9. Audit logging and activity

One JSON line per event on stdout (Cloud Run → Cloud Logging), with the fields
Cloud Logging interprets (`severity`, `message`, `logging.googleapis.com/labels`,
`logging.googleapis.com/trace`).

```json
{"severity":"INFO","message":"tool.call","event":"tool.call",
 "user":"u_3f9a1c2e7b4d","session":"s_91be…","client":"claude-ai",
 "tool":"search_messages","accounts":2,"outcome":"ok","duration_ms":412,
 "results":20,"fuzzy":true}
```

- `user` = HMAC-SHA256(pseudonym key, normalised primary address), truncated.
  Stable, not reversible without the key.
- Client IP on portal sign-in only with `AUDIT_LOG_CLIENT_IP=true` (default off).
- Events: `portal.login.*`, `oauth.consent`, `token.refresh`, `session.revoked`,
  `account.added/removed/test`, `tool.call`, `send.requested/confirmed/declined/
  sent/failed` (recipient **counts** internal/external/new, attachment count, size
  bucket), `policy.denied`, `ratelimit.hit`, `user.deleted`.
- **Never logged**: addresses (other than as pseudonym), subjects, bodies, folder
  names (only role), attachment names, search terms, tokens, passwords.
- **Own-activity feed** for the portal: the same events (without the pseudonym,
  plus account *names* the user chose) stored per user in the Store with a TTL
  (30 days). Users see what their AI clients did — transparency, and a GDPR plus.
- Admin insight: log-based metrics (active users, logins, failures, sends, errors
  per tool, fan-out latency), a small `universal-email-mcp audit` CLI summarising
  Cloud Logging per pseudonymous user, optional BigQuery sink.
- GDPR: keyed pseudonyms are still personal data for the key holder → dedicated
  log bucket with defined retention (90 days), documented purpose, DPIA
  template; in Austria works-council involvement may apply (ArbVG §96/96a) —
  noted in the docs, not legal advice.

## 10. Stored data (remote mode)

| Record | Content | Protection | Lifetime |
|---|---|---|---|
| user | pseudonym, portal identity ref, settings, default identity | profile fields encrypted | until deleted |
| account | server profile, username, password, permissions, display name | credentials encrypted | until removed |
| identity | addresses, name, signature, SMTP link | encrypted | until removed |
| oauth client | CIMD URL or DCR registration | — | TTL when unused |
| session | client, grants, token hashes, expiry | tokens hashed | 90 days default (configurable) |
| pending send | sealed draft reference, content hash | encrypted | minutes |
| activity | own events | encrypted | 30 days (TTL) |
| rate counters | per user/IP | — | window |

Encryption: AES-256-GCM, key ring from Secret Manager, versioned blobs → key
rotation without logouts. No mail content is ever persisted.

## 11. Deployment (reference: Google Cloud)

Public repo: generic `Dockerfile`, `cloudbuild.yaml`, `docs/deploy-gcp.md`.
Per-instance configuration and scripts belong in a separate (private) deployment repository.

- Cloud Build → Artifact Registry (version tag + instance tag).
- Cloud Run: `--allow-unauthenticated` (OAuth is ours), min 0, max N, no session
  affinity, 512 MiB, request timeout ~5 min.
- Secret Manager: credential key ring, pseudonym key, request-state sealing key,
  portal cookie key; OIDC client secret if SSO.
- Firestore (native) with TTL policies.
- Dedicated log bucket + log-based metrics + alerting (scripted).
- Optional static egress IP (Direct VPC egress + Cloud NAT, ≈ 35–40 USD/month).
  Ports 465/587/993/995 are open on Cloud Run.

The container is not GCP-specific: memory store for dev, SQLite store later for a
single VM / on-prem, text logs outside Cloud Run.

## 15. Decisions so far

- Name: `universal-email-mcp`. Copyright ARJOMA FlexCo, author Harald Schilly
  <info@arjoma.at>.
- Per-user login; v1 capabilities: read, organize (mark/move), delete (= Trash),
  drafts, send (send switchable).
- Two run modes (`local` stdio, `remote` multi-user) from one code base.
- Several accounts per user (IMAP/POP3/SMTP, per-account permissions, default
  identity); cross-account search; fuzzy matching with rapidfuzz.
- No permanent delete in v1; `delete_messages` = move to Trash, its own
  destructive-annotated tool so the chat client asks explicitly.
- Sessions: 30 days sliding, 90 days absolute by default; both configurable by
  the operator, including unlimited (absolute max = 0).
- Gmail / Google Workspace and Microsoft 365 out of scope for now.
- Attachment understanding (PDF etc.) → later, see `TODO.md`.
- Mail servers users may add: operator list `MAIL_SERVERS` (one = fixed,
  several = dropdown, unset = free entry with SSRF guards) — §5.
- Static egress IP: not planned; documented as an optional deployment step.
- Portal sign-in (v1): primary mailbox address + password against the
  operator-assigned server (`LOGIN_DOMAINS`); OIDC SSO later.
- Send fallback when the client can't confirm: `send-unless-flagged` by default
  (operator can choose `send | portal | draft`).
- Audit logs: 90 days retention; admins may de-pseudonymise via the audit CLI
  with the pseudonym key; client IP on portal sign-in is logged only when
  `AUDIT_LOG_CLIENT_IP=true` (default off).
- Shared mailboxes (v1): each user adds them with the shared credentials;
  admin-managed sharing later.
- Fresh design on MCP SDK 2.x.
