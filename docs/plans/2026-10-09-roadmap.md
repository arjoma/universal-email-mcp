# universal-email-mcp — roadmap from M1 to 0.1.0

Status: 2026-10-09 · companion to the design plan
([`2026-09-30-design.md`](2026-09-30-design.md), "§n" below refers to it).
Each work package (WP) is one feature branch and one PR, built by a focused
subagent and followed by a review (see `AGENTS.md`). Sizes: S ≈ a day,
M ≈ a few days, L ≈ a week or more of agent work plus review.

## Where we are

| Milestone | State |
|---|---|
| M0 skeleton, CI, PyPI placeholder | done |
| M1 read-only, multi-account, local stdio | code done, 328 tests; **not yet used against a real mailbox** |
| M2 full tool set locally | not started |
| M3 remote mode (OAuth, portal, Cloud Run) | not started |
| M4 hardening, docs, 0.1.0 | not started |

What exists: IMAP read path (EXAMINE only — nothing can change a mailbox yet),
the seven read tools, fuzzy matching, cursors, escaping/defanging, `probe`,
TOML config with accounts, identities, policy and limits (identities and the send
policy are parsed but not used yet). Missing entirely: SMTP, POP3, any write
operation, HTTP transport, OAuth, portal, store, encryption, audit log,
container image.

## Step 0 — local testing (now, before M2)

Real use decides whether the tool surface, the fuzzy thresholds and the table
output work, and M2 needs facts from a real mailbox.

- **0a Real mailbox, read-only** (no code needed): `config.local.toml` + `.env`
  in the checkout, password in the keyring, `probe`, then Claude Code with the
  stdio server — see "Local testing" in `AGENTS.md`. Collect: probe output for the
  `united-domains` preset (capabilities, SPECIAL-USE, namespace, where the
  webmail's "archive" puts mail), and every rough edge from a few days of use.
  Findings → issues or `TODO.md`.
- **0b Sandbox mailbox** (S): `scripts/dev-mailbox` starts the Dovecot image
  from the integration tests with podman, seeds realistic and hostile mail
  (reuse the seeding helpers) and writes a matching `sandbox.local.toml`. Later
  extended with an SMTP sink (e.g. Mailpit) for M2. All write operations are
  tried here first.

## M2 — full tool set locally

Order matters: organize first (smallest step from read-only to read-write), then
drafts, then send (the riskiest), POP3 is independent.

| WP | Content | Size |
|---|---|---|
| **2a Organize** | read-write `ImapSession` (SELECT only where needed, UID-scoped ops), `mark_messages`, `move_messages`, `delete_messages` (Trash via MOVE, else COPY + `\Deleted` + UID EXPUNGE with UIDPLUS, else refuse), `create_folder`; permission checks; tools the policy forbids are not registered; batch caps; header-index invalidation | M |
| **2b Folders as labels** | `archive_messages` (find `\Archive`, detect flat/yearly/monthly scheme, create year folder), `file_conversation` (collect the conversation across INBOX/Sent/folders, show, move), ambiguity → choice. Needs the archive scheme from 0a | M |
| **2c Drafts** | identities in the service layer, sender selection (§5), MIME composition (new/reply/reply-all/forward, `In-Reply-To`/`References`, quoting, signature, forwarding attachments from existing mail only), APPEND to Drafts, `create_draft`, `update_draft` | M |
| **2d Send** | SMTP backend over `mail/net.py` (implicit TLS / STARTTLS, verified), recipient trust check (sent-to history, internal domains, look-alikes — §7.1), policy (`send` modes, allowed domains, max recipients, rate limit), confirmation via elicitation, fallback, Sent copy, draft removal, `file_replies` auto-filing (§7.2.4); SMTP sink in the integration tests | L |
| **2e POP3** | POP3 backend (`TOP`/`UIDL`, newest-N header cache, never `DELE`) in `list/search/get`; POP3 server in the integration tests | M |
| **2f Phase-2 read tools** | `get_attachment` (small text inline, files as embedded resource, size caps), `mailbox_overview` | S–M |
| **2g M1 leftovers** | the "M1 review leftovers" in `TODO.md` (time zone of time windows, flag staleness, bare domains, cursor resume, thread dedupe) | S |
| **2h Presets** | validate `united-domains` with real probe output; add more presets only with probe evidence | S |

Decision needed before 2d — **send confirmation in local mode**: there is no
portal, so the remote fallbacks `portal` and `send-unless-flagged` (which parks
flagged sends in the portal) do not exist. Proposal: elicitation when the client
supports it, otherwise `draft` (the mail stays in Drafts, the user sends it from
the mail client); `send` only by explicit config.

## M3 — remote mode (first production pilot)

The largest milestone. Split so each PR is usable and testable on its own.

| WP | Content | Size |
|---|---|---|
| **3a HTTP skeleton** | Starlette app, `/mcp` (stateless 2026-07-28 + legacy stateless), `/health`, `/ready`, operator config from env (`MAIL_SERVERS`, `LOGIN_DOMAINS`, limits, policy), `universal-email-mcp serve`, Dockerfile | M |
| **3b Store + crypto** | `Store` interface (memory, Firestore), AES-256-GCM key ring with versioned blobs, users/accounts/identities/sessions records (§10), TTLs | M |
| **3c OAuth 2.1 AS** | `/authorize`, `/token`, `/revoke`, metadata (RFC 9728, 8414), PKCE S256, RFC 8707 audience, RFC 9207 `iss`, refresh rotation, lifetimes (§6.1), hashed tokens, CIMD (SSRF-safe fetch) + DCR fallback | L |
| **3d Portal core** | sign-in via `LOGIN_DOMAINS`, accounts (add/test/permissions/remove), identities, consent page with grants, connected clients; Jinja2, CSP, CSRF, secure cookies, re-auth for sensitive actions; **i18n-ready** (strings through a translation layer, English only; operator default language + user switch prepared) | L |
| **3e Per-user service** | `MailService` built per request from the store instead of TOML, grants enforced per call, `reauth_required`, per-instance connection pool caps | M |
| **3f Send in remote mode** | request-state sealing for confirmations, fallback per `SEND_FALLBACK`; "pending approvals" page (moved here from M4 because `send-unless-flagged` needs it) | M |
| **3g Message viewer** | `/m/<id>`: message, thread, raw headers, `.eml`, attachment downloads streamed from IMAP; sandboxed iframe, CSP, `nosniff` (§6.2); viewer links in tool results | M |
| **3h Audit log** | JSON events to stdout with pseudonyms (§9), own-activity feed in the store | S–M |
| **3i Deployment** | `cloudbuild.yaml`, `docs/deploy-gcp.md` (generic); instance config in the private deploy repo; first Cloud Run pilot | M |

## M4 — 0.1.0

- Portal: activity page, privacy page (export, delete everything).
- Rate limits (portal sign-in, sends, tool calls).
- Admin: `universal-email-mcp audit` CLI, log-based metrics and alerts.
- Docs: admin guide, user guide, GDPR notes and DPIA template.
- German translation of the end-user UI (second language).
- Security review of the whole code base (external pair of eyes welcome).
- MCP client matrix (§12): Claude.ai, Claude Desktop, Claude Code, ChatGPT,
  MCP Inspector.
- Release 0.1.0 to PyPI.

## Suggested order

0a → 0b → 2a → 2h → 2b → 2c → 2d → 2e/2f/2g (any order) → 3a → 3b → 3c → 3d →
3e → 3f → 3g → 3h → 3i (pilot) → M4.

Later items (OIDC SSO, attachment understanding, SQLite store, JMAP, XOAUTH2,
admin-managed shared mailboxes) stay in `TODO.md`.
