# universal-email-mcp — roadmap from M1 to 0.1.0

Status: 2026-10-09 · companion to the design plan
([`2026-09-30-design.md`](2026-09-30-design.md), "§n" below refers to it).
Each work package (WP) is one feature branch and one PR, built by a focused
subagent and followed by a review (see `AGENTS.md`). Sizes: S ≈ a day,
M ≈ a few days, L ≈ a week or more of agent work plus review.

## Where we are

| Milestone | State |
|---|---|

| M1 read-only, multi-account, local stdio | code done, 328 tests; **not yet used against a real mailbox** |

What exists: IMAP read path, and since WP 2a the organize operations (mark, move,
delete = move to Trash, create folder) on a read-write session,
the read tools (since WP 2-0: `account_info`, `list_folders`, `find_messages`,
`get_message`, `find_contacts`), fuzzy and wildcard matching, cursors, escaping/defanging, `probe`,
TOML config with accounts, identities, policy and limits (identities and the send
policy are parsed but not used yet). Missing entirely: SMTP, POP3, any write
operation, HTTP transport, OAuth, portal, store, encryption, audit log,
container image.

## Step 0 — local testing (now, before M2)

Real use decides whether the tool surface, the fuzzy thresholds and the table
output work, and M2 needs facts from a real mailbox.

- **0a Real mailbox, read-only** (no code needed): `config.local.toml` + `.env`
  in the checkout, password in the keyring, `probe`, then Claude Code with the
  stdio server — see "Local testing" in `AGENTS.md`. Collect: probe output for the
  `united-domains` preset (capabilities, SPECIAL-USE, namespace, where the
  webmail's "archive" puts mail), and every rough edge from a few days of use.
  Findings → issues or `TODO.md`.
- **0b Sandbox mailbox** (S, done — PR #6): `scripts/dev_mailbox.py` starts the Dovecot image
  from the integration tests with podman, seeds realistic and hostile mail
  (reuse the seeding helpers) and writes a matching `sandbox.local.toml`. Later
  extended with an SMTP sink (e.g. Mailpit) for M2. All write operations are
  tried here first.

## M2 — full tool set locally

Order matters: first the tool surface (2-0) while nobody depends on the M1 tool
names, then organize (smallest step from read-only to read-write), drafts, and
send (the riskiest); POP3 is independent.

### Tool surface (decided 2026-10-09)

Few, coarse tools, **split by risk, not by feature**: MCP clients let users set
approval per tool (always allow / ask), and annotations like `destructiveHint`
are per tool, so read, organize, delete, draft and send stay separate tools.
Variants become parameters. No server-side lazy discovery or meta-tool: it would
defeat per-tool approval, clients already defer large tool lists themselves, and
`tools/list_changed` is not reliably available (stateless transport). The
dynamic part is the **permission filter**: tools the policy, the account
permissions or (remote) the client's grants do not allow are not registered.

| Risk | Tool | Replaces / covers |
|---|---|---|
| read | `account_info` | config, permissions, overview (absorbs `mailbox_overview`) |
| read | `list_folders` | |
| read | `find_messages` | `list_messages` + `search_messages` (a time window is just a criterion) |
| read | `get_message` | `thread=true` replaces `get_thread` |
| read | `get_attachment` | |
| read | `find_contacts` | |
| organize | `mark_messages` | |
| organize | `move_messages` | `to="archive"` and `with_conversation=true` replace `archive_messages` / `file_conversation` |
| organize | `create_folder` | |
| delete | `delete_messages` | own tool (destructive, own approval) |
| drafts | `save_draft` | `create_draft` + `update_draft` |
| send | `send_message` | `send_draft` + `send_message` (by draft id or new) |

A read-only user sees six tools, a user with every permission twelve.

**Lists: overview first, then drill down.** Every list tool returns a bounded
overview plus a footer saying how to narrow it (limit + cursor, never everything
at once). Search parameters are one `query` everywhere: containing `*` or `?` it
is a case-insensitive wildcard pattern (umlaut-folded, starting at a word
start; for folders without `/` the folder's own name, with `/` the path, where
`*` also crosses levels), otherwise a fuzzy (rapidfuzz) match.

- `list_folders()` — top level only, each folder with its number of subfolders
  ("Clients ▸ 87"); `parent=` lists the children of a folder (fuzzy-resolved,
  ambiguity → choice); `query=` a flat list of matches with full paths;
  `depth=` (capped) for more levels; no match → similar names. Filtering runs on
  the cached folder list, not via IMAP `LIST` patterns (case-sensitive, mUTF-7).
  Counts (STATUS) only for the folders shown, capped; `limit` + cursor for wide
  levels.
- `find_contacts()` — without `query` a cheap overview: INBOX + Sent of the last
  7 days, at most ~100–200 headers per account, the 20 most recent contacts, and
  a hint to pass `query=` to find a person. With `query` a deeper window
  (default 180 days, capped, incremental header cache); no match → how far back it
  looked, similar names, `days=` to go further. `sent_to` (the user has written to
  them) stays: the send-time recipient check builds on it.

Decided 2026-10-09 — **send confirmation in local mode**: there is no portal, so
the remote fallbacks `portal` and `send-unless-flagged` (which parks flagged
sends in the portal) do not exist. Local mode uses elicitation when the client
supports it, otherwise `draft` (the mail stays in Drafts, the user sends it from
the mail client); `send` only by explicit config.
